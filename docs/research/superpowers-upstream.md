# Superpowers upstream package research

Checked 2026-10-16 against upstream HEAD commit [`bb92a77741419a4ab5f06e711a283343f1ada0c3`](https://github.com/obra/superpowers/commit/bb92a77741419a4ab5f06e711a283343f1ada0c3), whose Claude, Codex and npm manifests identify version **7.0.0**. This is a source inspection, not an installation or compatibility test. Links below are pinned to that commit. No upstream code was executed.

## Installation and runtime integration

The [README](https://github.com/obra/superpowers/blob/bb92a77741419a4ab5f06e711a283343f1ada0c3/README.md#installation) explicitly says installation differs by harness and to install separately for each harness.

| Harness | Documented installation | Runtime integration |
|---|---|---|
| Claude Code | `/plugin install superpowers@claude-plugins-official`; alternative: `/plugin marketplace add obra/superpowers-marketplace`, then `/plugin install superpowers@superpowers-marketplace` | Native plugin discovery plus the `SessionStart` command hook. |
| Codex App | Plugins sidebar, Coding section, Superpowers, install prompts | Native skill discovery; the Codex manifest deliberately declares empty hooks. |
| Codex CLI | `/plugins`, search `superpowers`, select `Install Plugin` | Same native plugin/skills approach. |

Sources: [README](https://github.com/obra/superpowers/blob/bb92a77741419a4ab5f06e711a283343f1ada0c3/README.md#installation), [Claude manifest](https://github.com/obra/superpowers/blob/bb92a77741419a4ab5f06e711a283343f1ada0c3/.claude-plugin/plugin.json), [Codex manifest](https://github.com/obra/superpowers/blob/bb92a77741419a4ab5f06e711a283343f1ada0c3/.codex-plugin/plugin.json), [porting guide integration table](https://github.com/obra/superpowers/blob/bb92a77741419a4ab5f06e711a283343f1ada0c3/docs/porting-to-a-new-harness.md#appendix-a--reference-integrations-current).

The checked tree has no `.codex/INSTALL.md`. Older clone/symlink Codex installation advice must not be presented as this version's documented installation mechanism. The README does not document a CLI command for unattended Codex plugin installation, a version-pinning install flag, or an offline installation contract. Those need separate harness documentation/validation.

For Claude, [hooks/hooks.json](https://github.com/obra/superpowers/blob/bb92a77741419a4ab5f06e711a283343f1ada0c3/hooks/hooks.json) matches `startup|clear|compact`, synchronously invokes `"${CLAUDE_PLUGIN_ROOT}/hooks/run-hook.cmd" session-start`, and declares `shell: "bash"`. [hooks/session-start](https://github.com/obra/superpowers/blob/bb92a77741419a4ab5f06e711a283343f1ada0c3/hooks/session-start) derives the package root from its own location, reads `skills/using-superpowers/SKILL.md`, and emits Claude's `hookSpecificOutput.additionalContext`. Copying individual skill files omits that bootstrap.

For Codex, [plugin.json](https://github.com/obra/superpowers/blob/bb92a77741419a4ab5f06e711a283343f1ada0c3/.codex-plugin/plugin.json) declares `skills: "./skills/"`, `hooks: {}`, and assets relative to the package root. [using-superpowers](https://github.com/obra/superpowers/blob/bb92a77741419a4ab5f06e711a283343f1ada0c3/skills/using-superpowers/SKILL.md) uses its description to trigger at conversation start, references per-platform tool mappings, and explicitly gives user instructions precedence over skills. This is different from Claude's hook injection; a successful file copy alone does not prove automatic activation.

## Package contents and boundaries

This is a multi-component plugin repository, not merely independent `SKILL.md` documents. The tree contains 15 skill directories, supporting references, prompt templates, Bash helpers, an optional Node/browser visual companion, hook scripts, assets and manifests for multiple harnesses. Other integrations include Antigravity, Cursor, Devin, Gemini, Hermes, Kimi, Muse, OpenCode and Pi. There is no root `agents/` directory of standalone agent definitions in this snapshot; review/implementation agents are principally prompt templates invoked by the skills.

Sources: [pinned tree](https://github.com/obra/superpowers/tree/bb92a77741419a4ab5f06e711a283343f1ada0c3), [skills](https://github.com/obra/superpowers/tree/bb92a77741419a4ab5f06e711a283343f1ada0c3/skills), [package.json](https://github.com/obra/superpowers/blob/bb92a77741419a4ab5f06e711a283343f1ada0c3/package.json), [requesting-code-review](https://github.com/obra/superpowers/blob/bb92a77741419a4ab5f06e711a283343f1ada0c3/skills/requesting-code-review/SKILL.md).

Preserve package-relative structure and cross-skill dependencies. For example, [executing-plans/scripts/task-start](https://github.com/obra/superpowers/blob/bb92a77741419a4ab5f06e711a283343f1ada0c3/skills/executing-plans/scripts/task-start) resolves `../../subagent-driven-development/scripts` relative to itself. The [visual server](https://github.com/obra/superpowers/blob/bb92a77741419a4ab5f06e711a283343f1ada0c3/skills/brainstorming/scripts/server.cjs) reads sibling `frame-template.html` and `helper.js` and searches the package root for its version. Installing selected skills independently can break these relationships.

The whole source repository is not the required runtime payload for every harness. The new [Codex packaging script](https://github.com/obra/superpowers/blob/bb92a77741419a4ab5f06e711a283343f1ada0c3/scripts/package-codex-plugin.sh) explicitly exports a rootless archive containing `.codex-plugin/`, `assets/`, `skills/`, README, license and code of conduct; it excludes root hooks, other harness manifests, docs, tests and development scripts. It also imports **OpenAI-owned `skills/*/agents/openai.yaml` metadata from a prior official package**, failing if metadata is missing for any skill. That metadata is not in this source tree, so packaging the GitHub checkout alone does not reproduce the official artifact. The older [fork-sync script](https://github.com/obra/superpowers/blob/bb92a77741419a4ab5f06e711a283343f1ada0c3/scripts/sync-to-codex-plugin.sh) similarly preserves destination-owned metadata. The porting guide still describes fork sync; the packaging script calls it the old flow. Treat the exact currently published marketplace artifact and provenance as unverified.

## Dependencies and portability

- **No third-party runtime npm dependencies does not mean no runtime tools.** Root [package.json](https://github.com/obra/superpowers/blob/bb92a77741419a4ab5f06e711a283343f1ada0c3/package.json) has no dependency declarations. Hooks and workflow helpers require Bash; helpers use Git and common Unix utilities such as awk, sed, grep, wc and dirname. The optional visual companion requires Node and a browser and uses Node built-ins. Packaging/developer utilities require additional programs, but these are not end-user runtime requirements. Sources: [hook wrapper](https://github.com/obra/superpowers/blob/bb92a77741419a4ab5f06e711a283343f1ada0c3/hooks/run-hook.cmd), [task-brief](https://github.com/obra/superpowers/blob/bb92a77741419a4ab5f06e711a283343f1ada0c3/skills/subagent-driven-development/scripts/task-brief), [review-package](https://github.com/obra/superpowers/blob/bb92a77741419a4ab5f06e711a283343f1ada0c3/skills/subagent-driven-development/scripts/review-package), [start-server](https://github.com/obra/superpowers/blob/bb92a77741419a4ab5f06e711a283343f1ada0c3/skills/brainstorming/scripts/start-server.sh), [server.cjs](https://github.com/obra/superpowers/blob/bb92a77741419a4ab5f06e711a283343f1ada0c3/skills/brainstorming/scripts/server.cjs).
- **Windows support relies on a Unix-like shell.** The polyglot `.cmd` hook searches standard/per-user Git for Windows locations, then suitable Bash executables on PATH; it skips WSL launcher aliases. With no Bash found it exits successfully without context injection, so exit code alone is insufficient health evidence. The optional visual server has Windows/MSYS-specific process handling and switches to foreground mode because Git Bash can reap background processes. Sources: [wrapper](https://github.com/obra/superpowers/blob/bb92a77741419a4ab5f06e711a283343f1ada0c3/hooks/run-hook.cmd), [start-server](https://github.com/obra/superpowers/blob/bb92a77741419a4ab5f06e711a283343f1ada0c3/skills/brainstorming/scripts/start-server.sh).
- **Executable permissions still matter in this snapshot.** The [porting guide](https://github.com/obra/superpowers/blob/bb92a77741419a4ab5f06e711a283343f1ada0c3/docs/porting-to-a-new-harness.md#part-6--distribution-and-release) documents marketplace extraction losing modes and recommends explicit `bash`/`node` invocations. `task-brief` and `review-package` invoke `sdd-workspace` through Bash, but [task-start](https://github.com/obra/superpowers/blob/bb92a77741419a4ab5f06e711a283343f1ada0c3/skills/executing-plans/scripts/task-start) and [task-done](https://github.com/obra/superpowers/blob/bb92a77741419a4ab5f06e711a283343f1ada0c3/skills/executing-plans/scripts/task-done) still directly invoke sibling helpers. Do not assume losing executable bits is harmless.
- **Offline support is not guaranteed.** Most skill prose and local helper operations are local after installation, but model access, marketplace availability and project-specific setup are outside that claim. The optional visual companion loads a remote versioned branding image by default; `SUPERPOWERS_DISABLE_TELEMETRY`, `DISABLE_TELEMETRY`, or `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC` can suppress it. Sources: [README telemetry](https://github.com/obra/superpowers/blob/bb92a77741419a4ab5f06e711a283343f1ada0c3/README.md#visual-companion-telemetry), [server implementation](https://github.com/obra/superpowers/blob/bb92a77741419a4ab5f06e711a283343f1ada0c3/skills/brainstorming/scripts/server.cjs).
- **Multiple agents require harness capabilities and policy choices.** The [Codex mapping](https://github.com/obra/superpowers/blob/bb92a77741419a4ab5f06e711a283343f1ada0c3/skills/using-superpowers/references/codex-tools.md) asks for `features.multi_agent`, discusses differing V1/V2 tools, isolated context, model/effort routing and optional machine defaults. These are upstream guidance, not a reason for an installer to silently overwrite personal settings; actual tool schemas take precedence. [SDD](https://github.com/obra/superpowers/blob/bb92a77741419a4ab5f06e711a283343f1ada0c3/skills/subagent-driven-development/SKILL.md) dispatches implementers/reviewers, prohibits concurrent implementation agents and provides inline-plan execution as an alternative when subagents are unavailable.
- **Shared installation does not isolate simultaneous workflows.** [sdd-workspace](https://github.com/obra/superpowers/blob/bb92a77741419a4ab5f06e711a283343f1ada0c3/skills/subagent-driven-development/scripts/sdd-workspace) puts artifacts under the current working tree's `.superpowers/sdd/<plan-basename>/`, with plan-path disambiguation. [task-brief](https://github.com/obra/superpowers/blob/bb92a77741419a4ab5f06e711a283343f1ada0c3/skills/subagent-driven-development/scripts/task-brief) explicitly says concurrent runs of the same plan in the same working tree share output. Separate worktrees are still needed for independent runs of the same plan.

## Integration implications and remaining questions

These are deductions from the source, not an implementation proposal: distinguish a package revision from its skills; keep hidden manifests, assets, references, helpers and relative relationships; project each harness's required payload through its supported installation mechanism; keep runtime dependency checks and activation checks separate from file existence. Native per-harness installation and raw skill copying are observably different behaviors.

Before promising unattended managed support, verify: (1) each installed harness version's supported plugin-install, enable, disable and remove APIs; (2) exact-version pinning and rollback semantics; (3) how to identify and avoid a duplicate existing installation; (4) official Codex artifact revision/metadata provenance; (5) whether artifact caches permit supported offline restore; (6) actual startup/compaction activation on Windows, including missing Bash; and (7) coexistence and precedence when other installed skills have the same names. The inspected upstream sources do not establish those contracts.

## Fit with Spinup today

Local inspection used Spinup commit `aebe28de44aed273716ebfa4bd22f0339e0632ad`.

- [The skills manifest](../../internal/skills/manifest.go) maps source strings to skill names and modes. It has no explicit package identity, resolved revision, artifact digest, or target-specific installation record.
- [The manager](../../internal/skills/manager.go) invokes `npx skills add`, caches fetched content by skill name, and skips fetching/installing when the corresponding `SKILL.md` already exists. This does not implement revision-aware package updates.
- [Library snapshots](../../internal/library/files.go) share an allowlisted set of paths, skip hidden files and symbolic links, have a 64 MiB content limit, and serialize path/data without executable mode. Simply placing an expanded plugin under `fetched/` would lose important packaging information.
- [Skill storage](../../internal/skills/store.go) parks unlisted skills in its store. Any new installer that publishes into that store must coordinate ownership and desired inventory with the existing manager. Native plugin caches outside the store are a different case.
- [Agent targets](../../internal/skills/agents.go) are the currently resolved Claude and Codex homes. [Agent configuration docs](../AGENT-CONFIG.md#separate-normal-and-proxy-providers) explain that this does not discover all isolated provider homes. Target identity must distinguish tool installations on the same machine.
- [Library policy](../LIBRARY.md#what-stays-on-each-machine) already calls for sharing portable capability requests while keeping plugin installation state, connection details and credentials local. This is the right starting point.

## Architecture proposed during research

This section records the pre-implementation proposal. The delivered behavior, including the single `packages.json` declaration and lock, is documented in [Plugin packages](../PACKAGES.md).

Add one package-management module, provisionally `internal/packages`, while keeping standalone skills supported through `internal/skills`. Its small interface separates three operations: resolve an explicitly requested revision/artifact; plan changes against observed target state; apply that plan and return typed outcomes. Resolution may access the network on explicit add/update. Reconciliation uses a locked resolution and must not silently select a newer release.

The portable declaration records package identity, source and intended targets/scope. A lock records the resolved source revision and each target's actual artifact identity/digest: the source commit alone is insufficient when a marketplace adds metadata. Publish declaration and lock as one consistent generation. Illustrative filenames are `packages.json` and `packages.lock`; neither exists today. Keep machine paths, credentials, native plugin state and Spinup ownership receipts local.

Start with two concrete adapters, Claude and Codex, behind the module's internal seam. They inspect supported capabilities and translate package operations to each tool's supported native mechanism. Source formats can be detected or handled by a narrow declarative recipe; do not require upstream projects to adopt a Spinup manifest. Avoid arbitrary shell installation recipes and a general dependency solver in the first version. Do not claim pinning, rollback or offline installation where the target does not support them: return an explicit unsupported or pending result, with a supported assisted installation path when necessary.

The module owns package identity, version comparison, conflicts, planning and receipts; adapters own target-specific discovery and activation. `internal/library` owns portable data and artifact exchange, `internal/service` schedules reconciliation, `internal/api` owns any new wire shapes, and `cmd/spinup` prints plans/results. This keeps package-by-tool special cases out of service and CLI code. Models, subscriptions and delegation preferences remain personal settings.

Required behavior:

1. Namespace internal package identity by source/owner/package. Separately check exposed skill names and overlapping workflows; storage namespaces alone do not solve runtime conflicts. Preserve package-relative references, and do not rewrite upstream skill names automatically.
2. Record exactly what Spinup created or adopted. Disable/remove only owned resources; detect external installations and local edits before replacing them. Coordinate with existing skill parking when a target shares that store.
3. Stage and validate content before activation; serialize mutations per target, recheck observed state, retain the last working revision, and record partial failures. Native manager operations are not assumed to form a cross-tool atomic transaction. Re-running reconciliation must converge without duplicate hooks or repeated installs.
4. Preserve hidden manifests and executable metadata through a deliberately defined artifact format. Validate extraction paths and link policy; do not broadly remove the existing library exclusions. Cache immutable payloads by digest and reuse them across targets where identical. For larger libraries, exchange artifact inventories and transfer only missing digests rather than embedding every package in every whole-library snapshot. Add protocol/version compatibility before sending new data to old clients; do not merely raise the current size limit.
5. Check prerequisites and activation, not just file presence or installer exit status. Report target-specific outcomes such as ready, unsupported, conflict, missing dependency or missing artifact. An unattended daemon must not start an interactive install loop.

Suggested delivery sequence: first validate the native adapter contracts on supported tool versions; then a local vertical slice for one package with inspect/plan/install/remove and ownership; then revision-aware updates and recovery; finally portable synchronization of declarations, lock and supported artifacts. Keep existing skills compatible during migration. Add project scope when a supported target needs it, without turning this first slice into a general plugin runtime.

Acceptance cases should cover repeated reconciliation, pre-existing native installs, duplicate skill names, interrupted activation, user edits, unavailable artifacts, unsupported host versions, Windows without Bash, retained executable metadata on Unix, multiple local tool homes, stale plans and older sync peers. Source inspection does not replace these integration checks. No package installation or code change was made during this research.
